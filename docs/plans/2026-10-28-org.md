# Plan: dia org

Status: **not started**.
Date: 2026-10-28
Driven by: `PRODUCT.md`: dia is a meta harness in which an org of hired agents works toward the user's objectives, the user steers the decisions the agents make, and agents improve the harness.
PRD: `docs/prds/org.md`.
Decisions: ADR-0032 (org of hired role agents), ADR-0033 (decision path and decision queue), ADR-0034 (task memory and retros), ADR-0035 (tiered self-improvement).
Depends on: `docs/plans/2026-10-23-agent-os.md`. Steps 1 and 2 of that plan (projects, tabs, agent overview) have landed. Its steps 6 and 7 are replaced by step 4 of this plan; its steps 3, 4, 5 and 8 continue alongside this plan.
Verified against: repo at commit `fbd4fad`.

## Rules for every step

* Each step lands on `main` as its own change, and dia must be usable for dogfooding after it.
* Every feature is a built-in plugin that uses only the plugin API a user plugin can use (ADR-0019). Only `plugins/claude-code` imports the Agent SDK (ADR-0029).
* A step that adds a screen designs it with `/impeccable` against fixture data, and passes its finish review against `DESIGN.md`, before wiring real data.
* Each step ends with `pnpm typecheck`, `pnpm lint`, `pnpm test` and a manual run of the installed build.

## Step 1 — Org core

Scope: Host built-in feature plugin, shared schemas in `src/shared` (ADR-0013), and the claude-code adapter's session options (ADR-0029). Implements ADR-0032.

1. Schemas in `src/shared` for a role (name, built-in flag, enabled flag, instructions, skills, MCP servers, optional allow/ask/deny lists), a hired agent (role, optional name), an objective (project, title, description, priority, assignee or unassigned, state), a task (objective, parent task, title, state, assigned hired agent) and the org settings (overall cap, objective watcher role).
2. Ship the built-in roles `planner`, `engineer`, `reviewer`, `researcher` and `retro`. The user can disable, copy and edit each one.
3. Hire and dismiss agents. The number of hired agents of a role is that role's cap.
4. Scheduler: start waiting tasks while both the overall cap and the role's cap have a free slot, by objective priority, then oldest first. Ad-hoc tabs are not counted. Decide in this step when a hired agent holds a slot (open question in `docs/prds/org.md`), and record the decision in ADR-0032.
5. `AgentSessionOptions` (`src/host/session/agent-backend.ts`) gets the fields a role needs: instructions to append to the system prompt, allowed and disallowed tools, and MCP servers. The claude-code adapter maps them to SDK options; an `ask` entry routes to `canUseTool`. If agent OS step 5 (#16) has landed, reuse its system-prompt field.
6. An unassigned objective starts a session of the objective watcher role, which calls `create_task` and `update_task` (served from `src/host/session/dia-tools.ts`). An objective assigned to a hired agent starts that agent with the same tools. Until step 2 lands, the user approves the task list as a whole.
7. A hired agent's active session appears in the agent overview and opens like a tab, with the live transcript and the composer's `queue` and `steer` modes. Decide in this step whether it is a tab in the task's project labelled with the agent's name, or a row in an org group (open question in `docs/prds/org.md`), and design it with `/impeccable`.
8. Screens: the org (roles and hired agents), the org settings (overall cap, objective watcher), and an objective with its tasks.

Done when: PRD goals 1 and 5 hold, with the task list approved as a whole in place of the decision path.

## Step 2 — Decision path and decision queue

Scope: Host built-in feature plugin and renderer screens. Implements ADR-0033.

1. `record_decision` and the decision schema: question, chosen answer, rejected alternatives, confidence, dependent tasks, and the commit of each affected task branch.
2. Plan review replaces step 1's whole-list approval: approve, or cut at a decision with guidance or a rejected alternative.
3. Cutting resets each affected task branch to the recorded commit, keeps discarded commits on a backup ref, discards dependent tasks, and starts the planner with the guidance.
4. A decision recorded during the work pauses its agent until the user accepts it or cuts there.
5. The decision queue lists plans, unreviewed decisions, `ask` permissions and, from step 4, harness changes. An item raises the same notification as a permission request.

Done when: PRD goals 2, 3 and 4 hold.

## Step 3 — Task transcripts, scratchpad, retro and long-term memory

Scope: Host built-in feature plugin. Implements ADR-0034.

1. Save every session's transcript against its task.
2. `scratchpad_read` and `scratchpad_write`, scoped to the task.
3. A task cannot reach `completed` until a `retro` session has read its transcripts and scratchpad.
4. `memory_search` and `memory_write` with project, environment and role scopes; a new session loads the entries in its scopes. Decide in this step where memory is stored (open question in `docs/prds/org.md`).
5. Record each read: count, last read time and reading task. Mark an entry stale after a configurable period.
6. A memory screen: browse, edit, and see read counts and stale entries.

Done when: PRD goals 6, 7 and 8 hold.

## Step 4 — `propose_change` and risk tiers

Scope: Host built-in feature plugin. Implements ADR-0035 and replaces agent OS steps 6 and 7.

1. `propose_change` with change type, change and evidence. A change in a git repo is made on a branch in a new worktree.
2. Tier settings per change type, with ADR-0035's defaults.
3. Apply-at-once changes are committed and listed in a change log with revert.
4. Queued changes appear in the decision queue with their evidence; approval merges, rejection deletes the branch and its worktree.
5. Meta agents get every registered project's directory as extra directories and read every task's transcripts (agent OS step 7, item 1).

Done when: PRD goal 9 holds, and `docs/prds/agent-os.md` goals 6 and 7 hold with `propose_change` in place of `meta_propose`.

## Step 5 — Workflows

Scope: Host built-in feature plugin.

1. A workflow schema: an ordered list of steps, each with a role.
2. Ship built-in workflows that the user can disable or copy; the user creates workflows.
3. A task follows its objective's workflow; each step runs a session of the step's role.

Done when: a task in an objective with a workflow of implement, review and retro runs one session of each role in order.

## Step 6 — Routines

Scope: Host built-in feature plugin. Uses Effect's `Clock` and `Schedule`.

1. A routine schema: schedule, project, prompt and role. dia ships no routines.
2. While dia runs, a routine creates a task at its scheduled time. Routine tasks skip decision path review (ADR-0033).

Done when: PRD goal 10 holds.

## Step 7 — Org KPIs and objective KPIs

Scope: Host built-in feature plugin and renderer screens.

1. Org KPIs computed by dia, as listed in `docs/prds/org.md` user story 22.
2. Objective KPIs: the user writes a KPI and its target; the assigned agent reports values with `report_kpi`.

Done when: an objective shows its KPI values reported by its agent, and the org screen shows the org KPIs for the last 7 days.

## Roadmap — not in this plan

* Adapters for agent harnesses other than Claude Code (ADR-0029).
* Objective KPIs read from a command or URL.
* Routines that run while dia is not running.
