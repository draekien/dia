# Plan: dia agent OS

Status: **in progress**: steps 1 and 2 have landed (`docs/designs/agent-overview.md`); steps 3-8 have not started.
Date: 2026-10-23
Driven by: `PRODUCT.md`: agents for registered projects run in the background, dia notifies the user when an agent needs input or has failed, an agent overview shows what every agent is doing, and a meta project reduces waste across every agent.
PRD: `docs/prds/agent-os.md`.
Decisions: ADR-0023 (tabs within registered projects), ADR-0024 (background agents), ADR-0025 (meta project).
Depends on: `docs/plans/2026-10-22-plugin-platform.md` (GitHub issues #6 to #9). Every step is a built-in plugin. Phases 1 to 3 (#6 to #8, f44499a and d6d37ed) and the worktrees step of Phase 4 (329d824, 5004cc8) have landed; the Phase 4 layout step is replaced by steps 2 and 3 of this plan.
Verified against: repo at commit `0209455`.

## Rules for every step

* Each step lands on `main` as its own change, and dia must be usable for dogfooding after it.
* A step that is a built-in plugin uses only the plugin API that a user plugin can use (ADR-0019).
* Each step ends with `pnpm typecheck`, `pnpm lint`, `pnpm test` and a manual run of the installed build.

## Step 1 — Project registry and tab model

Scope: Host built-in plugin and shared schemas (ADR-0023).

1. Schemas in `src/shared` for a project (directory, display name, whether it is a git repo, position in the user's order) and a tab (agent session, project, optional worktree, archived flag).
2. Registering a directory: detect whether it is a git repo; refuse a directory that is already registered.
3. Persist the project list, each project's tabs and the visible tab in place of the layout tree (ADR-0011). Existing panes migrate to tabs of a project created from each pane's `cwd`.
4. Reorder projects by dragging a project header, or from the keyboard (decided in `docs/designs/agent-overview.md`).

Done when: projects and tabs survive a restart with zero loss, and every pane from before the migration appears as a tab.

## Step 2 — Agent overview sidebar

Scope: renderer built-in plugin that replaces `src/renderer/src/components/pane-tree-view.tsx` and the split layout in `src/shared/domain/pane-tree.ts`. This step replaces the split-layout item of plugin platform Phase 4.

1. Build the sidebar with `/impeccable` against fixture data first (10+ projects, 20+ agents, every status, archived agents, an empty project, no projects), and pass its finish review against `DESIGN.md` (Agent Overview, Tabs, Status Indicator) before wiring real data.
2. Rows: status indicator, agent name, activity line (the `in_progress` item of the latest `TodoWrite`, else the last tool call; reuse `src/renderer/src/components/turn-activity-line.tsx` where it fits).
3. Meta group pinned above all projects with its open-proposal count; it shows no agents until step 5.
4. Fixed project order; inside a group, needs-input and failed agents sort first.
5. Collapsible project groups whose header shows the most urgent status and an agent count; a filter that matches agent and project names; `Ctrl+P` focuses it; arrow keys and `Enter` select rows.
6. Collapse to a status rail with one indicator per agent and the agent name in a tooltip.
7. States: first run with no projects ("Add project" with a directory picker), a project with no agents ("New agent").
8. Content header names the project and the agent.

Done when: PRD goals 5 and 9 hold, and the impeccable finish review has no open material findings.

## Step 3 — Archive and delete agents

Scope: Host built-in plugin and the overview's row actions.

1. Archive: remove the tab's worktree, keep its session transcripts, move the row into the project's collapsed "Archived" list.
2. Delete: remove the tab's worktree and its session transcripts, and remove the row.
3. An archived agent can be opened to read its transcript.

Done when: across repeated archive and delete cycles, zero orphaned worktrees remain, archived transcripts are readable, and deleted transcripts are gone.

## Step 4 — OS notifications

Scope: a Host built-in plugin decides when to notify; Electron main shows the notification, because the Host is a `utilityProcess` (ADR-0024).

1. Rule: a permission request, a question or a failure from an agent whose tab is not visible, or whose window is minimised or not focused, raises one notification. A finished turn raises none and marks the row finished.
2. Main exposes a notify request to the Host; the notification text names the project, the agent and the reason (`PRODUCT.md`, Accessibility & Inclusion).
3. Clicking the notification focuses the window and selects the agent's row.

Done when: PRD goals 1, 2 and 3 hold.

## Step 5 — Meta repo created and loaded into every agent

Scope: Host built-in plugin (ADR-0025). Only `plugins/claude-code` imports the Agent SDK (ADR-0029), so the kernel does not build `query()` options. This step adds the fields it needs to `AgentSessionOptions` (`src/host/session/agent-backend.ts`); the claude-code adapter maps them to SDK options.

1. On first start, create the meta repo under `userData`: `instructions.md` and `plugin/` with `.claude-plugin/plugin.json`.
2. `AgentSessionOptions` gets two fields: the text of `instructions.md` and the path of `plugin/`. Every agent dia starts receives both. The claude-code adapter sets `systemPrompt: { type: 'preset', preset: 'claude_code', append }` from the text and `plugins: [{ type: 'local', path }]` from the path. `settingSources` keeps its default.
3. A change merged into the meta repo applies to agents started after the merge.

Done when: a skill added to the meta repo is available in a new agent in every project, and agents started before the change are unaffected.

## Step 6 — `meta_propose` tool and proposal store

Scope: Host built-in plugin; the tool is served by the in-process MCP server that plugin platform Phase 3 added (`src/host/session/dia-tools.ts`).

1. `meta_propose` takes what went wrong and a suggested change, and records the project and agent that filed it.
2. Proposals are stored outside the meta repo, under `userData`.
3. `instructions.md` in the meta repo tells agents when to call `meta_propose`: a no-op tool call, a tool call that returned an error, or an expensive tool call.

Done when: a proposal filed by an agent in one project is listed for a meta agent with its project and agent.

## Step 7 — Meta agents: project access and branch approval

Scope: Host built-in plugin and the Meta group in the overview.

1. `AgentSessionOptions` gets a field for extra directories. A meta agent receives every registered project's directory in it, and the claude-code adapter sets the SDK option `additionalDirectories` from it. A meta agent reads the open proposals and every project's SDK transcripts.
2. A meta agent's change to the meta repo or to a git-repo project is made on a branch in a new worktree of that repo.
3. A meta agent's `Edit` or `Write` in a project that is not a git repo produces a permission prompt, whatever the meta tab's permission mode.
4. Each branch waiting for approval appears as a row in the Meta group; approving merges it, rejecting deletes the branch and its worktree.

Done when: PRD goals 6 and 7 hold.

## Step 8 — Meta repo push with secret scan

Scope: Host built-in plugin.

1. The user can add a remote to the meta repo and push.
2. dia scans the commits being pushed for secrets and refuses the push when the scan finds one. Choose the scanner in this step (open question in `docs/prds/agent-os.md`).

Done when: PRD goal 8 holds.

## Roadmap — not in this plan

* Keeping dia and its agents running in the system tray when the window closes (ADR-0024).
* Agents that keep running after dia quits; needs a Host that runs without Electron and ADR-0022's durable event store.
* Scheduled meta agent runs.
* Copying approved parts of the meta repo into `~/.claude`.
* An inbox view.
* Lifecycle rules that archive agents automatically.
* Other Claude Code users.
